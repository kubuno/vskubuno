# Kubuno desktop applications, written like Windows Forms — programming model

> Scope: product request (2026-09-30) "simplify the writing and organisation of the code like Windows Forms;
> controls and forms must be easy to create from code". A new Windows Forms project is three short files —
> `Program.cs` (`Application.Run(new Form1())`), `Form1.Designer.cs` (generated, never edited:
> `InitializeComponent()`, one field per control) and `Form1.cs` (the constructor calling
> `InitializeComponent()`, event handlers as plain methods). A Kubuno Desktop Application had a 60-line
> `main.rs` (file watcher, runtime, host options, chrome, client size, form options, the paint closure,
> `frame_typed`) and a view model with a hand-written `get`/`set` by string path. This note is the Kubuno
> equivalent of the Windows Forms model, as built. It builds on `docs/EVENTS.md` (events, the control
> hierarchy, the lifecycle) and `docs/XML_VIEWS.md` (the `.kbview` format); the rule of `CLAUDE.md` holds
> throughout: **the `.kbview` is the single source of truth, generated code is never written to disk.**

## 1. The three files

```rust
// main.rs — Program.cs
#![windows_subsystem = "windows"]
mod main_view;
fn main() -> kubuno::Result {
    kubuno::Application::run(main_view::MainView::new())
}
```

```xml
<!-- main_view.kbview — the design (Form1's designer surface) -->
<Panel DesignWidth="800" DesignHeight="450" Title="MyApp" OnLoad="main_view_load">
  <TextField x:Name="status" Placeholder="Status" X="24" Y="24" Width="632" Height="36" Anchor="Top, Left, Right"/>
  <Button x:Name="hello" Text="Say hello" Variant="Primary" OnClick="hello_click" X="672" Y="24" Width="104" Height="36" Anchor="Top, Right"/>
</Panel>
```

```rust
// main_view.rs — Form1.cs (Form1.Designer.cs is generated by the attribute, at compile time)
use kubuno::prelude::*;

#[kubuno::view("main_view.kbview")]
#[derive(Default)]
pub struct MainView {
    clicks: u32,
}

impl MainView {
    pub fn new() -> Self {
        let mut view = Self::default();
        view.initialize_component();
        view
    }

    fn main_view_load(&mut self, _sender: &Form, _e: &EventArgs) {
        self.status.set_text("Ready.");
    }

    fn hello_click(&mut self, _sender: &Button, _e: &MouseEventArgs) {
        self.clicks += 1;
        self.status.set_text(format!("Hello! ({} clicks)", self.clicks));
        self.hello.set_enabled(self.clicks < 10);
    }
}
```

`Cargo.toml` has **one** Kubuno dependency, `kubuno = { path = "…/src/crates/kubuno" }`.

| Windows Forms | Kubuno |
|---|---|
| `Application.Run(new Form1())` | `kubuno::Application::run(MainView::new())` |
| `ApplicationConfiguration.Initialize()` | optional: `Application::set_theme`, `set_chrome`, `enable_visual_styles`, `set_hot_reload`, `set_diagnostics` |
| `Form1.Designer.cs` | `#[kubuno::view("main_view.kbview")]` — generated in memory by the compiler, no file |
| `InitializeComponent()` | `self.initialize_component()` |
| `private Button button1;` | `hello: kubuno::forms::Button` (a field per `x:Name`, private unless the view's `Modifiers` says `Public`/`Internal`) |
| `this.button1.Enabled = false` | `self.hello.set_enabled(false)` |
| `this.Text = "…"`, `this.Close()` | `self.set_text("…")`, `self.close()` (the struct derefs to `kubuno::Form`) |
| `button1_Click(object sender, EventArgs e)` | `fn hello_click(&mut self, sender: &Button, e: &MouseEventArgs)` |

## 2. The `kubuno` crate (`desktop/windows/src/crates/kubuno`)

The facade an application depends on. It re-exports the layers (`kubuno::views` = `kubuno_views`,
`kubuno::controls` = `kubuno_controls`, `kubuno::ui` = `kubuno_ui`, `kubuno::events`, `kubuno::tracing`, and
`kubuno::data` = `kubuno_data` behind the opt-in `data` feature, which brings SQLx) and adds:

- `kubuno::forms`: `Control` and one typed handle per control (`Button`, `TextField`, `Label`, `CheckBox`,
  `Switch`, `Slider`, `ListBox`, `ComboBox`, `Panel`, `GroupBox`… — 42, the table
  `kubuno_views_meta::kbview::TYPED_CONTROLS`), `ControlCollection`, `Anchor`, `DockStyle`, `DialogResult`,
  `Form`, `AsControl`, `AsForm`, `ControlEvent`;
- `View`, the trait of what a window shows; `Application`; `MessageBox` (`MessageBoxButtons`,
  `MessageBoxIcon`); `Bindable`; `Result`/`Error`;
- `kubuno::prelude`: all of the above, the args types, `EventArgs` (**the root args struct under its Windows
  Forms name** — `e: &EventArgs` accepts any event), `UiHandle`, `UiDispatcher`, `Timer`, `spawn_local`,
  `delay`, `FormBorderStyle`, `StartPosition`.

The derive macros of `kubuno-views` (`#[derive(Component)]`, `#[derive(UserControl)]`, `#[derive(EventArgs)]`,
`#[event_handlers]`) generate `::kubuno_views::…` paths; in a package whose `Cargo.toml` depends on `kubuno`
and not on `kubuno-views` they are retargeted to `::kubuno::views::…` (`kubuno-views-macros/src/paths.rs`,
the `proc-macro-crate` approach), so custom controls work with the one dependency.

## 3. `#[kubuno::view]`

`#[kubuno::view("main_view.kbview")]` (relative to the Rust file, like `include_str!`), or
`#[kubuno::view(xml = "…")]` for an inline view (tests, samples). The macro (`kubuno-views-macros/src/view.rs`)
reads the view with the dependency-free reader `kubuno_views_meta::kbview::scan` and generates, in memory:

- **a field per `x:Name`d element**, typed with the handle of its control (`status: ::kubuno::forms::TextField`;
  `::kubuno::forms::Control` for a non-visual component, a structural element or a control of the crate),
  with a doc comment naming the element and its line (hover), spanned on the attribute's path (F12);
- a hidden `__kubuno_form: kubuno::Form` field, `Deref`/`DerefMut` to it;
- `initialize_component()`: links the fields to the view (by `x:Name`) and reads the view's values into
  them — `self.hello.get_text()` is `"Say hello"` right after it, before any window exists;
- `impl kubuno::View`: `form()`, and `handle_event`, **a `match` from each handler name the view uses to the
  struct's method of that name** — plain methods, in any `impl` of the struct, no attribute;
- `impl ViewModel`: the controls' bound values (§5), then the struct's `#[bind]` fields (`#[bind] user_name:
  String` answers `{Binding UserName}`; `#[bind("Path")]` names it), then one `#[data_context]` field (any
  `ViewModel`, a `kubuno-data` binding source…) for the other paths;
- `Default` (unless the struct derives it; a non-`Default` user field then fails at its own type with the
  usual error), `show()`, `show_dialog(owner)`;
- `const _ = include_str!("…")`: the view is **embedded** (a release build runs without the file) and
  **tracked** (saving the view rebuilds the crate).

**Handler signatures** (`kubuno::__private::Handler`, one impl per shape, chosen by the compiler from the
method's type): `fn f(&mut self)`; `fn f(&mut self, e: &A)` / `e: &mut A` (`&mut` to set `handled`/`cancel`;
`A` an args type, `&EventArgs` or `&dyn kubuno::events::EventArgs` for any event); `fn f(&mut self, sender: &S,
e: &A)` / `&mut A`; `fn f(&mut self, sender: &S)`; `async fn f(ui: UiHandle<Self>)` and `async fn f(ui:
UiHandle<Self>, e: A)` (a copy of read-only args, EVT-6). The sender `S` is `&Control` (any element), a typed
handle (`&Button`: the event must come from a `<Button>` or a class derived from it, else the handler is
skipped with a warning) or `&Form`.

**Compile errors** (all tested — `kubuno/src/view.rs` `compile_fail` doctests and
`kubuno-views-macros/src/view.rs` unit tests on the messages):

| Mistake | Message |
|---|---|
| unknown element with an `x:Name` | `main_view.kbview, line 3: unknown control `<Frobnicator>` (x:Name="f"): it is neither a Kubuno control nor a `#[derive(Component)]` / `#[derive(UserControl)]` type of this crate` |
| `x:Name` not an identifier | `…line 3: `x:Name="my-button"` is not a Rust identifier (letters, digits and `_`, not a keyword): rename the control` |
| two controls with one name / a name = a field | `…two controls are named `ok`` / `…the control `count` has the name of a field of `V`: rename one of them` |
| malformed view | `main_view.kbview, line 7: `</Panel>` closes `<Button>`` |
| a handler the struct does not have | rustc E0599 `no function or associated item named `ok_click` found for struct `V``, on the attribute |
| a method that is not a handler | E0277 `` `fn(&mut V, u32) {V::ok_click}` cannot handle an event of the view `V` `` + the list of accepted shapes |
| generic struct / not a struct / missing path | `a view cannot be generic…`, `` `#[kubuno::view]` goes on a struct…``, `the view is missing…` |

Controls of the crate (`<RoundButton x:Name="round">`) are found by scanning `src/**/*.rs` with the
language server's own reader (`kubuno_views_meta::scan_source`). A test of the `kubuno` crate keeps
`BUILTIN_ELEMENTS` equal to the registry, so a new built-in element (a `kubuno-data` component, say) must be
added there too.

## 4. Controls as objects

A `Control` is a cheap clonable handle (`Rc`) to one control of a form — an element of the view (a field of
the struct, or `form.control("name")`) or a control created in code. Getters are `get_*`/`is_*` (the builder
methods own the plain names: `Button::new().text("OK")`, `.name()`, `.location()`, `.size()`, `.bounds()`,
`.anchor()`, `.dock()`, `.enabled()`, `.visible()`, `.tool_tip()`, `.tab_index()`, `.property(name, value)`),
setters `set_*`. `get_text`/`set_text` map to the element's caption property (`Text`, else `Title` —
`GroupBox`, `Card` —, `Header`, `Label`), like Windows Forms' `Control.Text`. Per type: `checked`/
`is_checked`/`set_checked`/`checked_changed()` (CheckBox `Checked`, Switch `On`); `value`/`minimum`/`maximum`
and their getters/setters, `value_changed()` (Slider, NumericField, ProgressBar); `placeholder`, `read_only`
(text fields); `selected_index`, `selection_changed()` (ListBox, Tabs); `selected_value`,
`selected_value_changed()` (ComboBox, Dropdown); `items([…])`/`add_item` (list controls); `Button::variant`,
`Button::dialog_result`. Any property: `get_property`/`set_property`. Events: `click()`, `double_click()`,
`mouse_down/up/move/enter/leave()`, `key_down/up/press()`, `got_focus/lost_focus()`, `text_changed()`, and
`on::<A>("OnAnyEvent")`; on a typed handle the sender is typed too (`ok.click().subscribe(|sender: &Button,
e| …)`). Rust subscribers run after the handler the view names (Windows Forms: the designer's subscription
comes first); one that sets `handled` stops the next ones.

The form: `Form::new().text(…).client_size(w, h).start_position(…).form_border_style(…).maximize_box(…)
.minimize_box(…).property(…)`, `set_accept_button`/`set_cancel_button`, `controls()`, `control(name)`,
`add_to(container, control)` (into a panel of the view), `close()`, `dialog_result()`/`set_dialog_result()`
(a result on a modal form closes it), `is_open()`, `is_modal()`, `handle()`, and the events `load()`,
`shown()`, `activated()`, `deactivate()`, `form_closing()` (cancelable), `form_closed()`.

## 5. How a form reaches the runtime

Nothing is written to disk and `kubuno-views`' runtime is unchanged: a form's view is **composed in memory**
(`kubuno/src/forms/compose.rs`) and handed to `Runtime::reload_from_text`:

- the named controls' properties that code reads and writes (`Text`, `Title`, `Enabled`, `Visible`, `Checked`,
  `On`, `Value`, `Minimum`, `Maximum`, `SelectedIndex`, `SelectedValue`, `Placeholder`, `ReadOnly`, `Label`,
  `Description`, `Loading`, `Indeterminate`, `Invalid`, `ToolTip`, `Header` — when the element has them) are
  bound to the controls' values, `Text="{Binding __kb.3.Text, Mode=TwoWay}"`: setting one from code costs no
  recomposition, and what the user types lands in the control (`self.status.get_text()`); a property the view
  binds to the form's own data (`Text="{Binding Status}"`) stays bound to it — the handle reads it every frame
  and writes through it;
- every event attribute becomes `OnClick="__kb5"`, routed to the form (`ViewModel::dispatch_event`), which
  runs the handler the view named, the control's Rust subscribers, then a button's `DialogResult`; an event
  with Rust subscribers only gets such an attribute too;
- the controls created in code are appended as elements where they were added (the form's root, or a
  container of the view), with their geometry; changing a non-bound property, the geometry or the set of
  controls recomposes the view for the next frame (the router keeps its state by element id, so focus and
  hover survive).

`Runtime::frame_model(canvas, frame, &mut view, bounds)` (new in `kubuno-views`) paints with the view itself as
view model and hands posted closures and async tasks `&mut V`: `UiHandle<MainView>`, `View::dispatcher()`
(`UiDispatcher<MainView>`, Windows Forms' `BeginInvoke`) work on the struct. `Value` gained `From<bool/f32/f64/
i32/u32/usize/String/&str/Vec<Row>>` for `set_property`.

**`Application::run`** (`kubuno/src/application.rs`) installs the diagnostics sink, composes the view, opens
the window at the view's design size (`client_size`, `fit_work_area`, Kubuno chrome) with the view's `Form`
properties, and paints it every frame; in a debug build it reloads the `.kbview` when it is saved (the file
path recorded by the macro; a release build uses the embedded text). A view that does not compile shows its
first error in the window and logs them all against the view's own lines.

## 6. Several windows, modal dialogs (`kubuno-controls` host)

The host kept its per-window state (input queue, cursor, repaint request, close handler, title bar, caption
buttons, pending `Form` properties, drag state, accessibility tree…) in thread-locals: one window per UI
thread. It now keeps **one copy per window** and installs the one of the window a message is for while its
procedure runs (`host/window_tls.rs`, a stack discipline: a dialog's nested loop, opened from a frame of its
owner, restores the owner's state when it returns). On top of it:

- `host::run_with_options` from inside a running window opens a second window with a **nested loop** that ends
  when that window is destroyed; `HostOptions::owner` makes it an owned window (above its owner, no task bar
  button, `StartPosition::CenterParent` centres it on the owner), `HostOptions::modal` disables the thread's
  other host windows meanwhile and enables them again before it goes (so the activation returns to the owner);
- `host::run_scoped` is the same for a paint closure that borrows from the caller (`show_dialog(&mut self)`);
- `host::open_window` opens a modeless window on the running loop (`Form::show`); the main window's end closes
  the others (closing a Windows Forms application's main form ends it);
- `UiWaker` wakes every window of its thread; accessibility actions are queued per window; a paint delivered
  while a frame is rendering (a dialog's loop opened from that frame) waits for the frame's end instead of
  being re-requested for as long as the dialog is open.

`View::show_dialog(owner)` returns `DialogResult::Cancel` when the dialog is closed from its caption
(Windows Forms). `MessageBox::show_with` builds a small code-first form (icon, wrapped message, buttons with
their `DialogResult`, `AcceptButton`/`CancelButton`, `FixedDialog`, no task bar button) owned by the window
whose handler shows it.

## 7. Tooling

- **Language server** (`kubuno-views-ls`): a code-behind whose struct carries `#[kubuno::view]` is a *form
  class*; its inherent `impl`'s methods are its handlers (`code_behind::find_view_struct`/`find_view_impl`, used
  wherever the typed `#[event_handlers]` impl was: the handler set, missing/incompatible warnings, the ⚡
  dropdown, rename, removal of an untouched stub). `&Button`/`&TextField` parameters are typed senders,
  `&Control`/`&Form` any sender, `&EventArgs` the root args. `kubuno/createHandler` names a new handler the
  Windows Forms way — `hello_click` (`<x:Name>_<event>`), `main_view_load` for the view's own events on its root
  (the view's file name, like `Form1_Load`) — and writes a plain method into the struct's `impl` (one is added
  after the struct when there is none): `fn hello_click(&mut self, _sender: &Button, _e: &MouseEventArgs) { //
  TODO }` (the parameters are `_`-prefixed: nothing silences the unused-variable lint of a plain method); the
  prelude imported is `kubuno::prelude::*`.
- **rust-analyzer** expands the attribute: `self.status.` completes the `TextField` handle's methods, hover on
  `self.status` shows the generated doc (element and line), F12 goes to the `#[kubuno::view("…")]` attribute.
- **Visual Studio**: F7 in the designer now opens the view's code (`main_view.rs`, like Windows Forms opening `Form1.cs`;
  the XML when the view has no same-stem `.rs`), Shift+F7 in that code opens the designer; Solution Explorer nests it
  under the view (same stem, unchanged); a double-click on a control creates its default event's handler as above.
- **Templates**: *Kubuno Desktop Application* is the three files of §1 (the button without a handler, so the
  designer's double-click creates `hello_click`); *Kubuno View* (item) is a form class with a load handler and
  now runs `ControlItemWizard` (struct name, module declared in the crate root). The control item templates keep
  `kubuno_views::` paths; the wizard (`ControlItemNames.AdaptToProjectOnDisk`) rewrites them to `kubuno::views::`
  in a `kubuno`-only project, and adds a `kubuno` dependency next to `kubuno-views` when a form is added to a
  project created before this model. `tools/test-templates.ps1` instantiates all of them into the desktop
  application (a second form opened by the main one's `show_dialog`), builds with no warning, runs `cargo test`
  (the forms link their controls, the controls register) and runs the window.

## 8. Compatibility

Nothing of the previous model changed: `ViewModel` + `handlers!`, typed `#[event_handlers]` impls,
`Runtime::frame`/`frame_typed(_with)`, `FileWatcher`, `host::run_with_options` with one window. A project created
from the previous templates builds and runs unchanged (checked on a copy of such a project, §10). Both models mix
in one crate (a project may depend on `kubuno-views` and `kubuno` together).

## 9. Limits

- A property set on a control is shown at the next frame; `set_client_size` applies when the window opens (a
  window already open keeps its size).
- Rust subscribers holding clones of their own control (or of the form) keep them alive (an `Rc` cycle), as a
  Windows Forms lambda keeps its target: fine for controls that live as long as their form.
- `x:Name`s starting with `__` are reserved; the binding path prefix `__kb.` and the handler prefix `__kb` are the
  composition's.
- A handler added to the view while the application runs (hot reload) is only called after a rebuild (the
  `match` is compiled); the runtime logs "`x` is not a method of the view (rebuild after adding it)".
- The unknown-element check knows the built-in elements and the crate's own controls; a control of another crate
  would need to be declared in `BUILTIN_ELEMENTS` (none exists yet).
